# Описание API и логики работы Storage Service

Данный документ содержит описание основных эндпоинтов, механизмов аутентификации и необходимых зависимостей для работы сервиса.

## 1. Обязательные сервисы (Инфраструктура)

Для полноценной работы системы должны быть запущены следующие компоненты:

- **PostgreSQL:** Хранит метаданные файлов, настройки бакетов и данные пользователей (Better Auth).
- **MinIO:** S3-совместимое хранилище для физического размещения файлов.
- **Hasura GraphQL Engine:** Обеспечивает API для работы с метаданными и реализует систему прав доступа (RBAC).
- **Auth Service (`/auth`):** Управляет сессиями пользователей, регистрацией и входом.
- **Storage Service (`/storage`):** Основной API-шлюз для работы с файлами.

---

## 2. Эндпоинты Storage сервиса (`/storage`)

Все запросы к Storage Service проходят через `AuthGuard`, который поддерживает аутентификацию по сессионным кукам (JWT запланирован).

### Загрузка файла

- **URL:** `POST /storage/upload`
- **Формат:** `multipart/form-data` (поле `file`)
- **Логика:**
  1. Проверка прав пользователя и настроек бакета (размер, тип файла) через Hasura.
  2. Создание записи о файле в БД со статусом `is_uploaded: false`.
  3. Загрузка потока данных в MinIO (имя объекта = UUID файла).
  4. Обновление записи в БД: установка `is_uploaded: true` и сохранение `etag`.

### Скачивание файла

- **URL:** `GET /storage/download/:fileId`
- **Логика:**
  1. Проверка прав доступа к файлу через Hasura.
  2. Получение метаданных (оригинальное имя, MIME-тип).
  3. Стриминг данных напрямую из MinIO пользователю с подстановкой корректных заголовков.

### Удаление файла

- **URL:** `DELETE /storage/:fileId`
- **Логика:**
  1. Проверка прав на удаление.
  2. Удаление метаданных из PostgreSQL.
  3. Удаление объекта из MinIO.

### Получение временной ссылки

- **URL:** `GET /storage/presigned-url/:fileId?expiry=300`
- **Логика:** Генерирует прямую ссылку на MinIO, которая протухает через указанное время (в секундах).

---

## 3. Эндпоинты Auth сервиса

### Проверка для Hasura / Storage Service

- **URL:** `GET /hasura`
- **Логика:** Принимает куки пользователя, проверяет сессию в БД и возвращает заголовки `X-Hasura-User-Id` и `X-Hasura-Role`. Используется как Webhook для Hasura и внутренний метод проверки для Storage Service.

### Управление аккаунтом

- **URL:** `/api/auth/*` (стандартные эндпоинты Better Auth: `signin`, `signup`, `signout` и т.д.)

---

## 4. Механизмы AuthGuard

`AuthGuard` в Storage-сервисе отвечает за идентификацию пользователя и передачу его данных в Hasura. Он поддерживает несколько уровней проверки (в порядке приоритета):

1.  **Admin Secret Bypass (Service-to-Service):**

    - Если в заголовках запроса передан `x-hasura-admin-secret`, совпадающий с секретом в конфигурации, пользователь получает роль `admin`.
    - В этом режиме `X-Hasura-User-Id` не устанавливается, что позволяет Hasura работать в режиме полного доступа (bypass RLS).

2.  **JWT Authentication (Bearer Token):** (не тестировали, скорее всего не работает)

    - Проверяет заголовок `Authorization: Bearer <token>`.
    - Валидирует подпись JWT с использованием секрета `HASURA_GRAPHQL_JWT_SECRET` (алгоритм HS256).
    - Извлекает `X-Hasura-User-Id` и `X-Hasura-Roles` из claims (`https://hasura.io/jwt/claims`).

3.  **Session Cookie (Better Auth):**

    - Если JWT отсутствует или невалиден, Guard делает запрос к Auth-сервису (`GET BETTER_AUTH_API_URL/hasura`), проксируя все заголовки (включая куки).
    - Auth-сервис проверяет сессию в базе данных и возвращает JSON с заголовками `X-Hasura-User-Id` и `X-Hasura-Role`.
    - Это основной метод для работы через браузер.

4.  **Anonymous Access:**
    - Если ни один из методов выше не сработал, пользователю присваивается роль `anonymous`, а `X-Hasura-User-Id` остается пустым.
    - Доступ к конкретным файлам в этом случае определяется правами роли `anonymous` в метаданных Hasura.

---

## 5. Логика аутентификации и прав доступа

1.  **Аутентификация:** Основным механизмом является проверка сессионных кук. Storage Service проксирует куки в Auth-сервис для проверки сессии. Если сессия не найдена, пользователю присваивается роль `anonymous`.
2.  **Авторизация (RBAC):** Storage Service не содержит жесткой логики прав (кроме запрета на удаление анонимам). Все проверки "может ли этот пользователь видеть этот файл" делегированы **Hasura**. Сервис просто передает ID и Роль пользователя в каждый GraphQL запрос.

## 6. Работа с бакетами

Бакеты являются логическими контейнерами для файлов и настраиваются в таблице `storage.buckets`.

### Основные параметры бакета:

- **`name`**: Уникальное имя бакета (используется в MinIO и API).
- **`max_upload_size`**: Максимальный размер файла в байтах. Если файл больше, сервис вернет `400 Bad Request`.
- **`allowed_mime_types`**: Массив разрешенных типов файлов (например, `["image/jpeg", "application/pdf"]`).
- **`presigned_urls_enabled`**: Флаг, разрешающий или запрещающий генерацию временных ссылок для этого бакета.
- **`download_expiration`**: Время жизни временной ссылки по умолчанию (в секундах).

### Логика выбора бакета:

1.  При загрузке файла сервис использует бакет по умолчанию из переменной окружения `MINIO_DEFAULT_BUCKET_NAME`.
2.  Система поддерживает работу с несколькими бакетами. Сервис проверяет существование бакета в MinIO при старте и автоматически создает его, если он отсутствует.

## 6. Примеры использования

### Загрузка файла (cURL с использованием кук)

```bash
curl -X POST http://localhost:3001/storage/upload
  -b "better-auth.session_token=YOUR_SESSION_TOKEN"
  -F "file=@/path/to/your/file.jpg"
```

### Получение "вечной" публичной ссылки

Для того чтобы файл был доступен по постоянной ссылке без авторизации, необходимо:

1.  **В Hasura:** Настроить права доступа (Permissions) для роли `anonymous` на таблицу `storage.files` (разрешить `select`).
2.  **В Hasura:** Настроить права доступа для роли `anonymous` на таблицу `storage.buckets` (разрешить `select`).
3.  **Использовать эндпоинт скачивания:**
    `http://localhost:3001/storage/download/UUID-ФАЙЛА`

Такая ссылка не имеет срока годности. При каждом обращении сервис будет проверять права в Hasura, и если для `anonymous` чтение разрешено — файл будет отдан.

### Получение временной ссылки (Presigned URL)

```bash
# Ссылка протухнет через 10 минут (600 секунд)
curl -X GET "http://localhost:3001/storage/presigned-url/UUID-ФАЙЛА?expiry=600"
  -b "better-auth.session_token=YOUR_SESSION_TOKEN"
```

В ответ придет прямая ссылка на MinIO с подписью.
